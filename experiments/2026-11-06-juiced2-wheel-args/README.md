# Juiced2 per-car wheel state and sizing arguments

Question: can actual per-car stock TyreCode and native wheel-sizing arguments be established for held Juiced 2 cars, without guessed dimensions?

Result, qualified yes for three of six racer-relevant cars: the retained 94-record handling archive (Oversteer `juiced2-recovery`, SHA-pinned) carries per-car `TyreCode` strings (93/94 records, front and rear axle blocks). The audited sizing chain (renderer → 820F51C8 → setter 8210F798) then derives each car's native scale factors as a formula in the unresolved f4, with concrete values at the f4=1 assumption. Record-to-car identity has no archive join (three independent negative joins retained); attributions below are numeric-signature hypotheses cross-checked against sourced factory specs.

## New contract findings (bounded static trace)

- f4 origin: renderer `820F1DB0` loads f4 from `[context+684]+192` (selector 0/1) or `+176` (otherwise) immediately before calling `820F51C8` (recomp.55.cpp:4242-4265).
- ~~context+684 is initialized **NULL** in the constructor region `sub_821BC5xx`~~ — superseded by the static trace in [native sizing](../2026-11-06-juiced2-native-sizing/README.md): context+684 is the wheel constructor 820f0a28 second argument (the 9672-byte car object); the 821BC5xx NULL stores belong to other classes sharing offset 684. +176/+192 are per-car record data, so f4=1 is unverified.
- Mutable multiplier global `0x824CBE70`: initial float32 1.05 confirmed at decoded-image offset `0x4CBE70`; the reproducible `experiments/2026-11-06-juiced2-native-sizing/ppc_scan.py mult` (decoded `.text` section only; pairs `lis 0x824D`/`0x824C` with same-register loads, stores, `addi` and `ori` within 40 words) finds 4 loads, **0 stores and 0 address-taken uses** — no direct writer in `.text`; indirect writers, other sections and the race-time value stay unobserved. (Earlier wording "lis/addi scan of the whole decoded image" overstated the committed tool; corrected 2026-11-07.)
